# 嵌入式软件功能开发 Codex 协作 SOP 与提示词模板

## 1. 文档信息

- **文档版本**：V1.8
- **发布日期**：2026-08-18
- **适用范围**：嵌入式 C/C++、MCU/MPU、RTOS、GUI、设备控制、数据采集、存储和通信协议项目
- **目标读者**：产品、开发、测试、代码审查人员及使用 Codex 的团队成员
- **文档目的**：把需求澄清、方案评审、编码、验证、纠偏和交付固化为可复用流程，减少重复解释、无效重构和跨会话上下文丢失

本文不替代具体仓库中的 `AGENTS.md`、编码规范、架构文档、需求文档和测试规范。进入任何项目后，应先以当前仓库的实际规则、代码和用户最新结论为准。

## 2. 核心原则

团队使用 Codex 开发功能时，统一遵守以下原则：

1. **先读后改**：先阅读规则、架构、需求、调用链和同类实现，再提出方案或修改代码。
2. **证据优先**：不能仅根据文件名、变量名、截图或局部函数推断完整行为。
3. **复用优先**：优先使用项目已有模板、API、保存链路、刷新机制、提示接口和测试工具。
4. **最小改动**：需求未要求改变的回调顺序、页码、选中项、刷新时机、保存语义和错误处理必须保持不变。
5. **分清状态**：严格区分“已设计”“已编码”“构建通过”“模拟器验证”“目标板验证”“平台联调通过”和“可发布”。
6. **纠偏收敛**：收到用户新结论后，删除被否定的实现和文案，不能在旧方案上继续叠加兼容分支。
7. **文档闭环**：最终需求、实际设计、测试口径、协议差异和版本交付状态分别写入需求方案、设计方案、测试说明、协议变更和更新说明；长期稳定机制写入项目基础文档。
8. **明确未验证项**：模拟器、宿主编译或静态分析不能替代目标工具链、真实硬件和真实平台。
9. **审查后提交**：代码审查是 Git 提交前的最后一道质量门禁；候选差异发生任何变化后，原审查结论立即失效，必须重新审查。
10. **PR 基于事实**：PR 标题和说明必须根据实际提交、目标分支差异、验证记录和交付文档整理，不得根据聊天记忆补写未实现或未验证内容。

建议团队使用统一口诀：

> 先定位，后方案；先复用，后新增；小步修改，逐项验证；结论入文档，状态不夸大。

## 3. 四种工作模式

每次向 Codex 提交任务时，应明确当前属于哪种模式。模式不明确是返工的主要来源之一。

| 模式 | 允许的动作 | 默认交付物 | 是否修改代码 |
|---|---|---|---:|
| 评估模式 | 阅读需求、代码和文档，识别风险、缺口和依赖 | 问题清单、影响面、待确认事项 | 否 |
| 方案模式 | 给出数据流、调用链、修改范围、兼容和测试方案 | 可评审的软件方案 | 否 |
| 开发模式 | 按已确认方案修改、构建、验证并更新文档 | 代码、验证结果、剩余风险 | 是 |
| 审查模式 | 审查工作区、提交或分支差异 | 按严重程度排序的审查报告 | 否，除非明确要求修复 |

用户只说“分析”“评估”“确认方案”时，不应擅自修改代码。用户说“开始修改”“按方案实现”时，才进入开发模式。

## 4. 项目接入准备

### 4.1 每个仓库建议具备的上下文文件

| 文档 | 应包含内容 | 不应包含内容 |
|---|---|---|
| `AGENTS.md` | 公司或仓库编码规则、安全红线、工具约束 | 单次需求的具体实现结论 |
| 项目基础说明 | 硬件、工具链、架构、数据模型、公共机制、构建与验证方法 | 临时 BUG、未确认方案 |
| 版本化需求方案 | 业务规则、边界、验收口径、实施状态 | 大量代码实现细节 |
| 版本化设计方案 | 调用链、修改文件、接口复用、兼容策略、开发验证 | 未经确认的业务扩展 |
| 测试说明 | 环境、用例、边界、异常、阻塞项、发布条件 | 仅开发人员可理解的局部代码描述 |
| 协议变更 | 本版本相对基线的字段、命令、长度、语义、兼容和联调要求 | 未变化的完整协议重复副本、未经代码确认的字段 |
| 更新说明 | 版本范围、完成状态、验证证据、遗留风险、外部依赖和交付入口 | 每日工作流水、未验证的完成声明 |
| 代码审查规则 | 风险等级、检查清单和输出格式 | 与实际项目无关的机械规则 |

### 4.2 新会话接手顺序

1. 读取仓库根目录的 AI/开发规则。
2. 读取项目基础说明。
3. 读取当前版本需求方案、设计方案和测试说明；涉及平台、总线或外部设备时继续读取协议变更，阶段交付时读取更新说明。
4. 检查当前分支、提交号和工作区状态。
5. 确认已有改动的所有权，不还原用户改动。
6. 搜索当前任务相关源码、头文件、工程配置和同类实现。
7. 明确本轮工作模式和授权范围。

没有上述文档时，先让 Codex 只读梳理项目，并建立最小的项目基础说明。不要在完全不了解项目时直接开始跨模块重构。

## 5. 功能开发标准 SOP

### 5.1 阶段 A：需求输入与澄清

先把自然语言需求转换为可验证规则。至少确认：

- 功能入口和适用产品。
- 用户身份、运行模式和设备配置前提。
- 正常流程、取消流程、失败流程和恢复流程。
- 输入范围、单位、倍率、默认值和边界值。
- 配置是否保存，保存到哪里，何时保存。
- 是否影响协议、Flash/EEPROM、结构体长度或外部工具。
- 是否要求兼容旧配置、旧平台或旧外设固件。
- 哪些行为明确不修改。
- 验收环境是模拟器、目标板、平台还是联合设备。

澄清时优先提出会改变数据结构、协议兼容、控制安全或权限模型的问题。纯命名、像素和局部样式问题可以结合现有代码直接确认。

### 5.2 阶段 B：代码定位与既有能力调查

Codex 必须先形成调用链，而不是只找到一个看起来相关的函数。

#### GUI 功能至少检查

- 页面创建、父窗体和页面模板。
- 控件初始化、显示刷新、输入回调和退出销毁。
- 页面缓存、正式配置、保存按钮和返回按钮。
- 同类型成熟页面的布局和坐标计算。
- 已有定时刷新、提示、滚轮、数字输入和弹窗接口。
- 多语言资源、字体、外部二进制资源及生成工具。

#### 参数和持久化至少检查

- 结构体定义、对齐方式、字段类型和单位。
- 默认值、合法性检查、页面缓存和正式配置。
- `memcpy`、比较、保存、读取和协议序列化位置。
- FlashDB/EEPROM 的实际读取语义和失败行为。
- 旧版本结构长度、新字段初始化和升级策略。

#### 控制功能至少检查

- 输入状态、计算状态、控制状态和最终物理输出。
- 自动、手动、空舍、校准、报警、设备禁用和通信离线条件。
- 任务、中断、定时器和共享数据访问关系。
- 所有开启入口、关闭入口和异常恢复入口。

#### 协议功能至少检查

- 请求、回应、主动上传、ACK、超时、重试和分包。
- 消息 ID、设备 ID、长度、字节序和缓冲区容量。
- 平台、外设固件和设备端是否需要联合升级。
- 组帧是否意外修改正式配置或全局状态。

### 5.3 阶段 C：方案输出与人工确认

方案必须回答以下问题：

1. 修改哪些文件和函数。
2. 复用哪些现有接口。
3. 数据从哪里来，经过哪里，最终写到哪里。
4. 哪些结构、协议和公共模板不修改。
5. 旧配置或旧协议如何处理。
6. 并发和生命周期如何保证。
7. 失败时保持什么状态。
8. 如何验证，哪些环境当前无法验证。

方案中应把“必要修改”和“顺带发现的问题”分开。顺带发现的疑似缺陷没有用户确认时，不纳入本功能修改。

仓库存在 `.agents/skills/embedded-feature-plan/` 时，本阶段应显式调用 `$embedded-feature-plan`，保持只读调查并在方案确认前停止，不得提前实施代码。

### 5.4 阶段 D：任务拆分与提交策略

推荐按独立功能拆分开发和提交：

- 一个功能对应一个提交，便于审核、回滚和二分定位。
- 提交时只选择该功能相关文件，不混入模拟器产物、IDE 用户配置或其他未完成需求。
- 公共模板改动与业务页面改动可以同一提交，但必须列出受影响页面并扩大回归范围。
- 协议两端、设备与外设联合版本无法独立交付时，应在同一发布计划中管理，但代码仍可按职责拆分提交。
- 多个非常简单且完全同类的问题可以合并，但必须共享同一实现机制和测试矩阵。

本阶段只确定提交边界和拆分策略，不执行最终 Git 提交。实际暂存、最终代码审查和提交统一在阶段 I 完成。

以下情况不要合并一次修改：

- 功能之间涉及不同存储结构或不同外部依赖。
- 一个功能需要硬件验证，另一个只需界面验证。
- 一个功能尚有关键需求未确认。
- 合并后无法清楚判断回归失败由哪项引起。

### 5.5 阶段 E：编码实施

编码期间执行以下规则：

1. 修改前再次阅读目标函数的完整上下文和调用者。
2. 优先调用现有 API，不复制已有能力。
3. 只修改实现需求所需的最小代码块。
4. 不因个人偏好统一重排、重命名或格式化无关代码。
5. 保持原文件编码、BOM 和行尾格式。
6. 不改变公共模板的既有翻页、选择、回调、保存和退出语义。
7. 新增状态时明确置位者、读取者、清除者和跨重启需求。
8. 修改结构体前检查尺寸、偏移、协议长度和旧数据。
9. 修改控制输出时检查所有关闭、安全和异常路径。
10. 临时测试代码、场景钩子和生成文件不能混入正式提交。

### 5.6 阶段 F：开发自检

功能完成后，Codex 至少执行：

- 查看实际差异，确认没有无关文件和格式化噪声。
- 检查所有新增分支的 `return`、`continue`、`break` 和赋值位置。
- 检查数组边界、类型转换、单位和倍率。
- 检查新增状态是否在全部必要路径清除或恢复。
- 检查保存、取消、退出、失败和断电重启语义。
- 检查协议长度、最坏包长和缓冲区。
- 检查 GUI 首项、末项、空数据、满容量、重复进入和语言切换。
- 运行仓库既有格式、静态检查、单元测试和构建命令。
- 明确列出无法执行的 ARM 工具链、硬件或平台验证。

### 5.7 阶段 G：分层验证

| 验证层级 | 可以证明 | 不能证明 |
|---|---|---|
| 静态检查/代码走查 | 调用链、边界、明显控制流问题 | 实际时序和硬件行为 |
| 单元测试 | 纯算法、边界和确定性状态转换 | 外设、RTOS、GUI 集成 |
| 宿主编译 | 部分语法、声明和模拟器链接 | 目标 ABI、段布局和真实中断 |
| GUI 模拟器 | 页面布局、点击、缓存和索引 | 真实传感器、继电器和协议时序 |
| 目标工具链 | MCU 编译、链接、结构尺寸和资源占用 | 真实业务闭环 |
| 目标板 | 外设、控制输出、时序和断电行为 | 平台端处理正确性 |
| 真实平台/联合设备 | 端到端协议和联合版本 | 未覆盖的异常及长时间稳定性 |

测试结论必须写明层级。例如“模拟器构建通过”不能简写成“功能测试通过”。

### 5.8 阶段 H：文档与交付

阶段或版本功能完成后，按以下顺序整理文档：

1. 确认目标固件、对比基线、当前分支、候选实现状态和交付日期；提交号尚未生成时不得虚构。
2. 对照最新需求、实际代码、工作区差异和验证记录，删除旧方案及过期状态。
3. 生成或更新同一版本、同一日期的五份交付文档，并建立相互链接。
4. 固定需求编号，建立“需求编号 → 设计位置 → 测试用例 → 验证结果”追溯关系：需求方案拥有编号，设计方案维护设计映射，测试说明唯一维护完整矩阵，协议变更标注关联需求，更新说明只提供入口和状态摘要。
5. 协议没有变化时，协议变更仍应明确写明“本版本无协议变化”及核对范围，不能让协作方自行猜测。
6. 只有稳定架构、公共机制、工具链或文档入口变化时才更新项目基础说明。
7. 检查需求编号集合、相对链接、旧文件名残留、Markdown 格式、版本控制差异和临时产物。

五份交付文档在提交前只记录当时已经存在的分支、基线、提交或候选工作区状态，不强制填写尚未生成的最终提交号。最终提交号、提交列表和比较范围在提交后统一写入 PR 说明，不得仅为回填提交号修改已审查的五份文档或增加独立补录流程。

五份交付文档的职责如下：

| 文档 | 必须回答的问题 | 主要内容 |
|---|---|---|
| 需求方案 | 需要实现什么 | 最终业务规则、稳定需求编号、范围、边界、不实施项和验收口径 |
| 设计方案 | 实际如何实现 | 调用链、修改模块、复用接口、需求设计映射、数据流、兼容策略和开发验证 |
| 测试说明 | 应如何验证 | 唯一完整追溯矩阵、环境、用例、边界、异常、回归、阻塞项和发布条件 |
| 协议变更 | 外部协作方需要改什么 | 关联需求及相对基线的命令、字段、长度、单位、枚举、时序、兼容及联调清单 |
| 更新说明 | 本版本交付了什么 | 追溯矩阵入口、版本范围、完成状态、验证证据、遗留风险、外部依赖和文档入口 |

推荐使用四字简称和统一归档格式：

```text
<主题>需求方案_V<版本>_<YYYYMMDD>.md
<主题>设计方案_V<版本>_<YYYYMMDD>.md
<主题>测试说明_V<版本>_<YYYYMMDD>.md
<主题>协议变更_V<版本>_<YYYYMMDD>.md
<主题>更新说明_V<版本>_<YYYYMMDD>.md
```

同一次阶段交付的五份文档必须使用相同版本号和日期。被新基线完全替代的旧活动文件可删除，由 Git 历史负责追溯；存在法规、质量体系或正式审计要求时，按组织规则归档旧版本。

最终回复至少说明：

- 完成了什么。
- 修改了哪些关键文件或文档。
- 执行了哪些验证及结果。
- 哪些目标板、平台或外部依赖仍未验证。

### 5.9 阶段 I：提交前最终代码审查与 Git 提交

代码审查是功能提交 Git 仓库前的最后一道质量门禁，必须在编码、自检、分层验证、文档同步、测试产物清理和提交文件分组全部完成后执行。建议使用独立 Codex 审查任务，降低开发上下文带来的确认偏差。

按以下顺序执行：

1. 使用“提交前文件分组”确认本功能应提交和不得提交的文件，清理可再生成产物。
2. 由开发人员或经明确授权的 Codex 仅暂存本功能文件；不得使用 `git add .`、`git add -A` 等扩大范围的命令。
3. 启动独立只读审查任务；仓库存在 `.agents/skills/embedded-final-review/` 时显式调用 `$embedded-final-review`。完整阅读 `.team/rules/code_review.md`，以 `git diff --cached` 对应的已暂存差异作为最终候选提交；未暂存时必须明确基线、文件或提交范围，不能审查一个范围却提交另一个范围。
4. 审查必须结合完整调用链、需求、设计、测试、协议和构建配置，输出准确位置、触发条件、影响、风险等级及最小修复建议。
5. 🔴 高危问题必须阻断提交；🟡 中危问题必须修复，或由负责人给出可验证依据并记录接受结论；🔵 低危建议不默认阻断，但不得掩盖功能风险。
6. 发现阻断问题后退出审查模式，回到阶段 E 至 H 完成修复、受影响验证和文档同步，再重新分组、暂存并执行完整最终审查。不得用同一次旧审查结论覆盖修改后的差异。
7. 审查结论为“🟢 良好（无阻断问题）”后，确认暂存差异自审查以来未发生变化，再执行 `git diff --cached --check`、核对 `git status` 和候选文件清单。
8. 只有用户或项目流程明确授权后才能创建 Git 提交。提交完成后保留实际提交号、提交列表、审查结论和仍需目标板或平台验证的项目，并在阶段 J 的 PR 说明中统一记录，不回填五份交付文档。

以下任一情况都会使最终审查失效，必须重新审查：

- 修改、增加、删除或重新暂存任何候选文件或代码块。
- 更改编译选项、工程配置、协议资源、字库或二进制资源。
- 修复审查发现后只做局部复核，没有重新查看完整候选差异。
- 实际提交范围与审查范围不一致。

审查通过不等于目标板测试、平台联调或版本验收通过。最终提交可以保留已明确记录的外部待测项，但不能把未执行验证写成已通过。

### 5.10 阶段 J：PR 标题与说明整理

最终代码审查通过并完成对应 Git 提交后，可以让 Codex 整理 PR 标题和说明。该步骤只生成可供开发人员审核的文本，不自动推送分支、不创建 PR、不修改仓库文件。

整理 PR 信息时必须：

1. 明确目标分支、来源分支和实际比较范围，优先使用 `目标分支...当前分支` 的提交及差异，而不是依赖聊天摘要。
2. 在 PR 说明中记录实际比较范围和提交列表，作为五份交付文档与最终源码版本之间的提交号关联入口。
3. 阅读相关需求方案、设计方案、测试说明、协议变更和更新说明，核对业务名称、兼容结论及外部依赖。
4. 只写当前 PR 实际包含的功能，不把其他工作区改动、后续计划或未提交内容混入说明。
5. 准确区分已执行验证、目标板待测、平台待测和外部依赖阻塞，不得把宿主构建或模拟器结果扩大为完整验收通过。
6. 协议、存储结构、版本宏、外设固件或平台协作有变化时，在说明中单独列出兼容与联调要求；没有变化时不虚构差异。
7. 标题保持单一主题、简洁可检索；说明至少包含提交范围、变更背景、主要修改、影响与兼容、验证结果、未验证及风险、文档或协议入口。
8. PR 创建、推送、指定审查人及发送外部通知都属于后续外部动作，必须由用户或团队流程另行明确授权。

## 6. 用户纠偏标准流程

用户指出“实现方式不对”“已有接口可用”“改动太多”时，按以下流程处理：

1. **暂停扩展**：停止继续沿当前方案增加代码。
2. **复述新结论**：用一到三句话说明新的最终规则和不再采用的旧方案。
3. **重新查证**：阅读用户指出的模板、接口、参考分支或同类页面完整上下文。
4. **比较差异**：明确当前实现与期望实现的差异，不只修改截图中的一行。
5. **收敛代码**：删除被否定的临时变量、重复 API、兼容分支和测试钩子。
6. **保持既有语义**：检查纠偏是否误改回调顺序、页面跳转、保存和控制状态。
7. **重新验证**：至少重跑受影响构建、边界和界面场景。
8. **同步文档**：删除旧方案文字，不能同时保留相互冲突的两套描述。

纠偏时禁止使用“再加一个标志”“再包一层函数”来掩盖错误抽象。先判断旧增量是否应该直接删除。

## 7. 高频返工原因与预防措施

| 返工原因 | 典型表现 | 强制预防动作 |
|---|---|---|
| 未检查现有 API | 重复创建定时器、提示框、保存函数 | 搜索同类页面及接口调用者，方案中列出复用项 |
| 只看局部截图 | 坐标、列宽、父窗体或标签样式不一致 | 找到用户指定模板，复用其计算和窗口层级 |
| 公共模板改动过大 | 删除后页码、选择项或回调行为变化 | 建立原行为基线，只增加独立状态刷新 |
| 直接修改正式配置 | 取消后数据已生效或提前写 Flash | 按页面缓存和统一退出保存链路实现 |
| 混淆逻辑和物理状态 | 常闭输出导致平台状态也反相 | 只在最终物理输出层转换 |
| 把短读当读取失败 | 新字段默认值或旧字段语义错误 | 阅读实际存储库代码并设计升级测试 |
| 模拟器过度建模 | 为看页面制造虚假控制数据 | 默认只模拟点击、布局、缓存和索引 |
| 临时变量不断增加 | 状态所有权不清、多个标志互相清除 | 为每个状态写清置位、读取、清除和生命周期 |
| 忽略外部依赖 | 固件已编码就宣称功能完成 | 单列平台、外设固件、加密库和生成工具阻塞 |
| 文档语态滞后 | 代码已完成，文档仍写待定位或仅方案 | 完成功能后立即更新实施状态矩阵 |
| 无关格式变化 | 审核 diff 困难、二进制或工程文件变化 | 修改前后检查编码、行尾和 `git diff --check` |

## 8. 提示词编写规则

高质量提示词应包含以下六项：

1. **任务模式**：评估、方案、开发或审查。
2. **上下文入口**：要求先读哪些规则和文档。
3. **业务目标**：最终要实现什么，而不仅是“修改某函数”。
4. **边界约束**：哪些模块、行为、结构和协议不能改。
5. **参考实现**：指定成熟页面、函数、分支或外部参考工程。
6. **验收方式**：需要哪些构建、模拟器、单元测试、硬件或平台验证。

提示词不需要预先规定所有代码细节。对尚未定位的项目，让 Codex 先调查现有机制并报告证据，通常比直接要求新建函数更稳妥。

### 8.1 日常任务通用前缀

大多数日常任务可以先填写下面六项，再按第 9 章追加专项要求：

```text
工作模式：<评估 / 方案 / 开发 / 审查>
任务目标：<最终业务效果>
上下文：先阅读仓库规则、项目基础说明、当前需求和相关调用链。
修改边界：<明确不能改变的行为、结构、协议或文件>
参考实现：<同类页面、现有 API、提交或参考工程>
验证要求：<静态检查 / 单元测试 / 模拟器 / 目标板 / 平台>

优先复用现有机制并做最小必要修改。已有工作区改动属于用户，不得还原；无法验证的项目必须明确列出。
```

### 8.2 选择提示词长度

- 已定位且边界明确的简单修改：使用通用前缀加 9.4。
- 涉及公共模板、存储、控制或协议：使用通用前缀加对应专项模板。
- 需求仍有歧义或用户要求先确认：使用 9.2 或 9.3，不授权修改。
- 前一版被用户否定：直接使用 9.11，不继续叠加补丁。
- 准备发布或长会话收尾：使用 9.12 和开发完成检查表。

```text
   - 按命令字、字段偏移、类型、长度、字节序、单位、倍率、范围、枚举、应答、序列、超时和兼容策略说明；
   - 提供修改前后对比、完整报文或字段示例、联调清单及双方版本组合；
   - 同步指出必须更新的完整协议文档；如果本版本无协议变化，明确写明“无协议变化”及已核对的接口范围，不虚构差异。
   - 变更总览为每项协议变化标注关联需求编号。

5. `<主题>更新说明_V<版本>_<YYYYMMDD>.md`
   - 汇总固件版本、硬件范围、对比基线、当前分支、已有提交或候选状态及交付状态；
   - 按已编码、不实施、仅回归、暂停和阻塞汇总功能；
   - 列出主要更新、兼容与升级、已有验证、交付前待办、发布限制和五份文档入口；
   - 这是版本交付摘要，不写每日工作流水。
   - 提供完整需求追溯矩阵的相对链接和覆盖状态摘要，不复制整张矩阵。

五份文档必须遵守以下一致性规则：

- 使用相同文档版本、发布日期、目标固件和对比基线；
- 文档标题使用“需求方案、设计方案、测试说明、协议变更、更新说明”四字简称；
- 建立有效的相对链接，项目基础说明中的当前文档入口同步更新；
- 需求方案、设计映射和测试追溯矩阵的需求编号集合必须完全一致；活动需求必须关联测试用例，暂停和不实施项必须写明处置原因；
- 需求、单位、默认值、结构长度、协议值、状态和待测项不得互相矛盾；
- 不得把代码走查、静态检查、单元测试、宿主构建或模拟器结果写成目标板、平台或验收通过；
- 旧配置、旧平台、旧外设和回退能力必须按实际结论说明；
- 最终提交号尚未生成时不得虚构；提交后由 PR 说明记录实际提交列表和比较范围，不为回填提交号重新修改五份文档；
- 被新基线替代且无需审计保留的旧活动文件可以删除，由 Git 历史追溯，不重复堆放；
- 不提交截图、日志、构建目录、生成文件、一次性测试钩子或个人配置。

完成后执行以下检查：

1. 检查五份文档的标题、版本、日期、固件版本和相互链接；
2. 检查需求方案、设计映射和测试追溯矩阵的编号集合一致，活动需求均有测试用例和验证状态；
3. 搜索旧文件名、旧版本号、被否定方案和“待定位”“完成后补充”等过期文字；
4. 检查所有相对链接均能解析；
5. 仓库存在交付文档校验脚本时执行该脚本；不存在时人工核对相同的编号集合、必填状态、链接和元数据规则，并执行 Markdown/空白检查及 `git diff --check`；
6. 查看 `git status` 和实际差异，确认没有修改业务代码或覆盖用户其他改动。

最终报告生成或重命名了哪些文档、协议是否变化、引用入口更新位置、执行的检查及仍需人工确认的内容。不要暂存或提交文件。
```

### 9.15 提交前最终代码审查

```text
使用 $embedded-final-review 执行 Git 提交前的最终代码审查，只读检查，不修改文件、不调整暂存区、不创建提交。

目标功能：<功能名称>
目标分支：<分支名称>
审查范围：已暂存候选差异（git diff --cached）
对比基线：<HEAD、目标分支或指定提交>

请先完整阅读 AGENTS.md、.team/rules/code_review.md、项目基础说明及本功能对应的需求方案、设计方案、测试说明和协议变更，再检查：
1. 已暂存文件是否与目标功能一致，是否混入用户改动、其他功能或生成物；
2. 完整 diff、调用链、数据结构、保存链路、控制状态、协议长度、并发和资源生命周期；
3. 已执行验证是否足以支持当前结论，文档状态是否与代码和验证一致；
4. 是否存在高危或中危问题，以及低危问题是否可能导致实际误用。

每项发现必须包含准确位置、触发条件、影响、风险等级和最小修复建议。最终明确给出以下一种门禁结论：
- 🔴 严重风险（阻断提交）；
- 🟡 中度隐患（需修复或形成经确认的接受依据后重新审查）；
- 🟢 良好（无阻断问题，可以进入提交确认）。

不要在本轮顺手修复。若候选差异在审查后发生任何变化，明确说明原审查结论失效，必须重新执行最终审查。
```

### 9.16 PR 标题和说明整理

```text
请根据当前分支的实际提交和差异整理 PR 标题与说明。本轮只输出文本，不修改文件、不推送分支、不创建 PR，也不发送外部通知。

目标分支：<例如 develop>
来源分支：<当前功能分支>
比较范围：<目标分支...来源分支，或明确提交范围>
PR 语言：<中文 / 英文>

开始前请阅读 AGENTS.md、项目基础说明、本功能对应的需求方案、设计方案、测试说明、协议变更、更新说明，以及实际提交列表和完整 diff。只描述当前比较范围内已经实现的内容，不根据聊天摘要补写功能。

请按以下格式输出：

1. PR 标题
   - 单行、单一主题、简洁可检索；
   - 体现核心业务变化，避免“更新代码”“修复问题”等无信息标题；
   - 除非仓库已有约定，不自行添加类型、作用域、工单号或版本前缀。

2. PR 说明
   ## 提交范围
   - 记录目标分支、来源分支、实际比较范围和本 PR 包含的提交列表。

   ## 变更背景
   - 说明为什么需要本次变更及对应需求范围。

   ## 主要修改
   - 按功能或模块概括实际差异，不逐文件复述提交。

   ## 影响与兼容
   - 说明硬件范围、旧配置、存储结构、协议、平台、外设固件和升级兼容；无相关变化时明确写“无相关变化”。

   ## 验证结果
   - 分层列出实际执行的静态检查、单元测试、宿主构建、模拟器、目标工具链、目标板和平台验证及结果。

   ## 未验证与风险
   - 列出仍需目标板、平台或联合设备验证的项目，以及已知发布限制和外部依赖；没有时写“无已知未验证项”，不得省略。

   ## 文档与协议
   - 列出需求方案、设计方案、测试说明、协议变更和更新说明入口；无协议变化时明确标注。

最后检查标题、说明、提交列表、实际 diff 和文档状态是否一致。发现比较范围不明确、存在未提交相关改动或审查仍有阻断问题时，先报告问题，不生成可直接提交的 PR 文案。
```

## 10. 开发完成检查表

### 10.1 需求与方案

- [ ] 最终需求、明确不做项和验收标准一致。
- [ ] 关键用户结论已经进入文档，而不是只存在于聊天中。
- [ ] 已检查同类代码和现有 API。
- [ ] 修改范围和不修改范围清楚。
- [ ] 外部依赖及联合版本明确。

### 10.2 代码

- [ ] 只包含最小必要修改。
- [ ] 没有无关格式化、编码或行尾变化。
- [ ] 没有重复 API、无用临时变量和被否定方案残留。
- [ ] 回调顺序、页面跳转、保存和错误处理保持原语义。
- [ ] 类型、范围、单位、索引和控制流已复核。
- [ ] 并发、ISR、生命周期和安全输出已评估。
- [ ] 持久化结构、旧数据和协议长度已评估。

### 10.3 验证

- [ ] 静态检查和实际 diff 已查看。
- [ ] 可执行单元测试全部通过。
- [ ] 宿主或模拟器构建结果已记录。
- [ ] GUI 使用真实页面和真实回调验证。
- [ ] 目标工具链构建状态明确。
- [ ] 目标板、平台和联合设备待测项明确。
- [ ] 测试产物已经清理且 `.gitignore` 未屏蔽必要源码。

### 10.4 交付

- [ ] 需求方案、设计方案、测试说明、协议变更和更新说明使用相同版本、日期、固件及对比基线。
- [ ] 五份文档职责清楚、相互链接有效，项目基础说明指向当前基线。
- [ ] 需求编号保持稳定；需求方案、设计映射和测试追溯矩阵编号集合一致。
- [ ] 测试说明唯一维护完整追溯矩阵；活动需求有测试用例和验证状态，暂停及不实施项有明确处置。
- [ ] 协议变更标注关联需求，更新说明提供追溯矩阵入口但不重复完整矩阵。
- [ ] 协议变化已形成面向协作方的差异说明并同步完整协议；无变化时已明确记录核对范围。
- [ ] 更新说明准确汇总完成项、不实施项、暂停项、阻塞项、验证证据和发布限制。
- [ ] 文档中没有旧文件名、被否定方案和过期实施状态。
- [ ] 每项状态使用统一词汇。
- [ ] 提交只包含对应功能文件。
- [ ] 二进制资源和工程文件变化有明确原因。
- [ ] 最终回复没有夸大验证结论。

### 10.5 最终审查与提交

- [ ] 已按功能明确提交文件清单，暂存区未混入其他需求、用户改动或生成物。
- [ ] 已使用独立只读审查任务检查最终候选差异，并完整读取仓库代码审查规则。
- [ ] 审查范围与实际准备提交的范围一致。
- [ ] 无未处理的高危问题；中危问题已修复，或已有负责人确认的可验证接受依据。
- [ ] 修复审查问题后已重新执行受影响验证、文档同步和完整最终审查。
- [ ] 最终审查通过后候选差异未再发生变化。
- [ ] `git diff --cached --check`、`git status` 和候选文件清单已复核。
- [ ] 已取得创建 Git 提交的明确授权；提交号、提交列表、审查结论和外部待测项将在 PR 说明中记录，不回填五份交付文档。

### 10.6 PR 标题与说明

- [ ] PR 标题和说明基于目标分支、来源分支、实际提交及完整差异生成。
- [ ] PR 说明已记录实际比较范围和提交列表，并与最终审查候选一致。
- [ ] 只包含当前 PR 的实际功能，没有混入未提交改动、后续计划或其他需求。
- [ ] 变更背景、主要修改、影响与兼容、验证、未验证及风险、文档与协议入口完整。
- [ ] 验证结论按层级表述，没有把低层级验证写成目标板、平台或验收通过。
- [ ] 协议、存储、版本和外部联合升级要求与交付文档一致。
- [ ] 生成 PR 文案时没有自动推送分支、创建 PR、指定审查人或发送通知。

## 11. 团队落地建议

1. 将本 SOP、`Codex仓库级Skills使用指南`、`.agents/skills/embedded-feature-plan/`、`.agents/skills/embedded-release-delivery/` 和 `.agents/skills/embedded-final-review/` 放入团队公共模板仓库，各项目维护自己的基础说明及版本化五份交付文档。
2. 每个新功能先使用“单个功能先出方案”模板；简单且边界明确的功能才直接开发。
3. 编码、验证、文档和文件分组完成后，固定使用独立只读任务执行“提交前最终代码审查”；审查通过且候选差异未变化时才允许提交。
4. Git 提交完成后使用“PR 标题和说明整理”模板记录实际提交范围并生成候选文案，不为补录提交号修改五份交付文档；经开发人员确认后再执行推送或创建 PR。
5. 用户发生两次以上纠偏时，停止继续打补丁，使用“用户纠偏”模板重新收敛方案和 diff。
6. 长会话每完成一个阶段就使用“阶段收尾和五份文档整理”模板更新仓库文档；新会话从文档接手，不依赖聊天摘要。
7. 每个团队项目维护统一的实施状态词汇，避免“已完成”含义不一致。

推荐状态词汇：

| 状态 | 定义 |
|---|---|
| 待确认 | 业务规则仍会影响方案 |
| 已确认 | 需求和边界已确定，尚未编码 |
| 已编码 | 代码已进入当前工作区或提交 |
| 开发验证完成 | 已完成指定静态、单元或模拟器验证 |
| 目标板待测 | 必须在真实硬件验证 |
| 平台待测 | 必须完成真实平台或可控桩验证 |
| 外部依赖阻塞 | 缺少库、工具、协议端或配套固件 |
| 暂停 | 当前版本明确不实施，保留后续立项条件 |
| 不实施 | 已确认保持现状，不进入本次发布 |
| 验收通过 | 需求规定的全部必要环境均已通过 |
