# Codex 仓库级 Skills 使用指南

## 1. 文档信息

- **文档版本**：V1.2
- **发布日期**：2026-08-18
- **适用范围**：使用 Codex 开展嵌入式软件需求分析、功能开发、阶段交付和提交审查的团队项目
- **目标读者**：产品、开发、测试、代码审查人员及使用 Codex 的团队成员
- **文档目的**：说明仓库级 Skills 的职责、调用时机、输入、输出、衔接顺序和使用示例

本文不替代根目录 `AGENTS.md`、团队开发 SOP、项目基础说明、版本化需求设计文档和代码审查规则。Skill 负责执行一个边界清楚的工作流，实际结论仍以当前仓库代码、配置、文档、验证证据和用户最新确认内容为准。

## 2. 三个 Skills 的职责

| Skill | 主要阶段 | 核心职责 | 默认是否修改文件 |
|---|---|---|---:|
| `$embedded-feature-plan` | 编码前 | 调查需求、调用链、数据流、现有 API、同类实现和影响范围，输出最小修改方案 | 否 |
| `$embedded-release-delivery` | 编码完成后的文档收尾；提交后的 PR 准备 | 生成或更新五份交付文档，检查一致性；根据实际提交整理 PR 标题和说明 | 文档任务是；PR 文案任务否 |
| `$embedded-final-review` | Git 提交前 | 对已暂存候选差异、Commit 或分支范围执行独立只读审查并给出门禁结论 | 否 |

三个 Skills 覆盖了功能开始前、功能完成后的文档闭环、提交前最终审查和提交后 PR 准备。编码实施、分层验证、提交文件分组、Git 暂存和创建提交仍按团队 SOP 及人工授权执行，不由一个通用 Skill 自动包办。

## 3. 标准使用顺序

```text
需求输入
  -> $embedded-feature-plan 调查并输出最小方案
  -> 人工确认方案
  -> 编码实施、开发自检和分层验证
  -> $embedded-release-delivery 更新五份交付文档
  -> 按 SOP 清理产物、分组文件并仅暂存当前功能
  -> $embedded-final-review 审查已暂存候选差异
      -> 有阻断问题：修复、重验、同步文档、重新暂存、重新完整审查
      -> 无阻断问题：取得授权后创建 Git 提交
  -> $embedded-release-delivery 根据实际提交整理 PR 标题和说明
  -> 人工确认后再推送或创建 PR
```

必须注意：五份交付文档在最终代码审查前完成；PR 文案在最终审查通过且 Git 提交完成后整理。五份文档不预填或回填尚未生成的最终提交号，实际提交列表和比较范围由 PR 说明统一记录。候选差异发生变化时，原最终审查结论立即失效。

## 4. 编码前：`$embedded-feature-plan`

### 4.1 什么时候使用

- 用户要求“先分析”“先评估”“先给方案”“确认后再修改”。
- 新功能涉及 GUI、配置、持久化、控制、RTOS、协议或多个模块。
- 不确定项目是否已有合适 API、页面模板、保存链路、定时器或提示接口。
- 从其他分支、产品或定制版本移植功能，需要先确定差异和最小移植范围。
- 修改可能影响结构体、旧配置、协议长度、物理输出或权限模型。

纯文字、单一坐标或已经完全确认且没有关联影响的一行修改，可直接按 SOP 的简单功能流程处理，不必机械调用。

### 4.2 调用示例

```text
使用 $embedded-feature-plan，为“<功能名称>”制定编码前软件方案。本轮只读调查，不修改代码和文档。

已确认需求：<最终业务规则>
明确不修改：<原有行为、结构或协议>
参考页面、接口或分支：<已知位置；没有可不填>

请阅读仓库规则、项目基础说明和当前需求设计文档，调查完整调用链、数据流、现有 API、同类实现、保存与失败路径、兼容和验证要求。输出最小修改方案、具体文件函数、复用结论、不修改范围、风险、验证矩阵和仅会改变方案的待确认问题。完成后等待确认，不实施代码。
```

### 4.3 预期输出

- 最终需求和非目标。
- 当前入口、调用链、数据流和状态所有权。
- 可直接复用、最小扩展或不适用的现有机制。
- 必要修改的文件、函数、数据和实施顺序。
- 明确保持不变的公共模板、回调、存储、协议和控制行为。
- 旧配置、旧平台、失败、安全和并发影响。
- 分层验证方案、外部依赖及建议提交边界。
- `Ready for confirmation` 或 `Blocked for clarification` 结论。

## 5. 编码完成后：`$embedded-release-delivery` 文档模式

### 5.1 什么时候使用

- 功能已经编码并完成当前可执行的自检和分层验证。
- 用户要求阶段收尾、整理交付资料或同步需求设计测试结论。
- 需求、实现、协议、验证状态或不实施项发生变化。
- 准备执行提交文件分组和最终代码审查。

### 5.2 调用示例

```text
使用 $embedded-release-delivery，根据当前仓库实际代码、Git 差异和验证记录更新本阶段五份交付文档。

交付主题：<主题>
目标固件：<版本>
对比基线：<版本、分支或提交>
文档版本和日期：<Vx.y / YYYY-MM-DD>
文档目录：<目录>

只修改交付文档，不修改业务代码，不暂存或提交。准确区分已编码、构建、模拟器、目标板、平台和验收状态；无协议变化时也要记录核对范围。完成后运行 Skill 自带的一致性校验。
```

### 5.3 预期输出

- 需求方案、设计方案、测试说明、协议变更和更新说明。
- 统一版本、日期、目标固件、对比基线和相对链接。
- 稳定需求编号，以及设计方案中的需求设计映射、测试说明中的唯一完整追溯矩阵、协议变更中的关联需求和更新说明中的矩阵入口。
- 实际实现、验证证据、未验证项、外部依赖和发布限制。
- 文档一致性校验结果，包括需求、设计、测试编号集合及活动需求测试覆盖。

## 6. 提交前：`$embedded-final-review`

### 6.1 使用前提

- 编码、自检、可执行验证和五份交付文档已经完成。
- 生成物已经清理，提交文件已经按功能分组。
- 仅当前功能的候选文件已经暂存。
- 工作区中其他用户改动和未完成需求未混入暂存区。

### 6.2 调用示例

```text
使用 $embedded-final-review 审查当前已暂存的候选提交。本轮只读，不修改文件、不调整暂存区、不运行会生成产物的构建或测试、不创建提交。

目标功能：<功能名称>
审查范围：git diff --cached
需求及交付文档：<入口>
已有验证：<命令和结果>

请完整读取仓库代码审查规则，记录候选文件、HEAD 和差异指纹，结合候选版本的完整调用链审查。按仓库规定输出问题、触发条件、影响、最小修复建议和明确门禁结论；结束前重新计算差异指纹，候选变化时判定本次审查失效。
```

### 6.3 门禁处理

- 高危问题阻断提交。
- 中危问题需要修复，或形成负责人确认的可验证接受依据；随后重新执行完整最终审查。
- 无阻断问题只表示当前候选差异可以进入提交确认，不代表目标板、平台或版本验收通过。
- 审查通过后任何候选文件、代码、资源、工程配置或暂存选择变化都会使结论失效。

## 7. 提交后：`$embedded-release-delivery` PR 模式

### 7.1 使用前提

- 最终审查已针对相同候选差异通过。
- 候选差异未再修改，并已完成对应 Git 提交。
- 目标分支、来源分支和比较范围明确。

### 7.2 调用示例

```text
使用 $embedded-release-delivery，根据实际 Git 提交和目标分支差异整理 PR 标题与说明。本轮只输出文本，不修改文件、不推送、不创建 PR。

目标分支：<目标分支>
来源分支：<来源分支>
比较范围：<目标分支...来源分支>
PR 语言：<中文或英文>

请核对五份交付文档、实际提交列表、完整差异和验证记录，在 PR 说明中记录实际比较范围和提交列表，只写当前 PR 已包含的内容，准确列出兼容、协议、未验证项和外部依赖。不要为回填最终提交号修改五份文档。
```

PR 创建、推送、指定审查人和发送通知属于外部操作，仍需单独授权。

## 8. 完整功能示例

以“为某类设备增加一个可保存参数”为例：

1. 使用 `$embedded-feature-plan` 调查页面缓存、正式配置、保存链路、结构体布局、旧数据读取、协议和同类输入控件，确认是否需要新增字段及迁移策略。
2. 人工确认方案后，进入普通开发任务完成最小代码修改。
3. 按方案执行静态检查、单元测试、模拟器、目标工具链、目标板或平台验证，并记录未执行项。
4. 使用 `$embedded-release-delivery` 更新五份交付文档，需求固定需求编号，设计维护设计映射，测试唯一维护完整“需求 → 设计 → 用例 → 结果”矩阵，协议标注关联需求，更新说明提供矩阵入口并汇总交付状态。
5. 按 SOP 清理生成物和分组文件，仅暂存该功能直接相关内容。
6. 使用 `$embedded-final-review` 审查 `git diff --cached`。若发现旧配置迁移或协议长度问题，修复后从受影响验证、文档同步和暂存步骤重新执行。
7. 审查通过并取得授权后创建 Git 提交。
8. 再次使用 `$embedded-release-delivery`，根据目标分支和实际提交生成 PR 标题与说明，并由 PR 记录实际提交列表和比较范围。

## 9. 快速选择

| 当前问题 | 应使用的 Skill |
|---|---|
| 还没编码，需要先确认怎么改 | `$embedded-feature-plan` |
| 已编码，需要整理五份交付文档 | `$embedded-release-delivery` 文档模式 |
| 已暂存，需要提交前最终审查 | `$embedded-final-review` |
| 已提交，需要准备 PR 标题和说明 | `$embedded-release-delivery` PR 模式 |
| 只需要实现已经确认的代码 | 不调用上述只读方案或审查 Skill，按 SOP 进入开发模式 |
| 只需要普通代码解释或诊断 | 直接提出解释或诊断任务，不机械调用交付 Skill |

## 10. 共同边界与维护

1. Skill 不替代 `AGENTS.md`、项目基础说明、团队 SOP 和代码审查规则。
2. 显式使用 `$skill-name` 可以减少错误触发；Codex 也可能根据 Skill 描述隐式选择。
3. 仓库级 Skills 必须位于 `.agents/skills/<skill-name>/`，并随项目模板提交，团队成员才能共同使用。
4. 新会话应先读取当前仓库事实，不依赖旧聊天摘要。
5. 工作区已有改动默认属于用户，三个 Skills 都不得擅自还原或扩大提交范围。
6. Skill 文件更新后应运行官方结构校验；若列表未及时出现，可重新打开 Codex 项目或重启 Codex。
7. 通用流程变化同步更新本指南、团队 SOP、README、项目基础入口和规则包版本。
8. 最终提交号只在提交后由 PR 说明关联；不得仅为补录提交号修改已审查的五份交付文档。
9. 五份文档使用同一需求编号体系；完整追溯矩阵只放测试说明，避免多处复制后状态不一致。
